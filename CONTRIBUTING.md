# Contributing

Use a focused issue or pull request that explains the concrete trigger, observed behavior and expected result. Keep changes small enough to review. Describe which checks passed and any platform or setup limits.

Start with the setup in the README. Run the relevant service tests while developing, then `npm run check` for a change that affects shared behavior. Browser and account tests must use synthetic local fixtures, without real employer submissions, mailbox data or paid model calls.

Preserve original documents, exact artifact review, current candidate/posting bindings and honest uncertain outcomes. A new adapter needs explicit identity, native field, upload and matching-confirmation checks. Never replace missing evidence with a guessed answer or generic success page.

Keep credentials, candidate documents, runtime databases, browser profiles, screenshots of real accounts, machine configuration and raw logs out of issues, pull requests and commits. Use made-up people and reserved example domains in reproductions. Check `git diff --cached` before committing.

Retain dependency licenses and legitimate authorship. New vendored code or assets need an explicit source, revision and compatible license. The MIT license applies to original project code; it does not relicense dependencies.
